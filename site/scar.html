SelfClusterAccessReview API

A single API call that answers: which workspaces does this user have access to?

Endpoint

HTTP endpoint
POST /services/access-virtual-workspace/apis/access.kcp.io/v1alpha1/selfclusteraccessreviews

Request

Callers authenticate with either a bearer token or trusted front-proxy headers.

curl examples
# Bearer token path
curl -k -X POST   -H "Authorization: Bearer $KCP_TOKEN"   https://root.kcp.example:6443/services/access-virtual-workspace/apis/access.kcp.io/v1alpha1/selfclusteraccessreviews

# Front-proxy path
curl -X POST   -H 'X-Remote-User: alice'   -H 'X-Remote-Group: eng'   http://localhost:9099/services/access-virtual-workspace/apis/access.kcp.io/v1alpha1/selfclusteraccessreviews

Response

JSON payload
{
  "kind": "SelfClusterAccessReview",
  "apiVersion": "access.kcp.io/v1alpha1",
  "status": {
    "clusters": [
      {
        "clusterName": "33daicwbox20zsxj",
        "endpoint": "https://root.kcp.example:6443/clusters/33daicwbox20zsxj"
      },
      {
        "clusterName": "workspace1",
        "endpoint": "https://root.kcp.example:6443/clusters/workspace1"
      }
    ]
  }
}

How it works

The RBAC provider watches ClusterRoleBindings and RoleBindings across opted-in workspaces, translates subjects into graph entries, and stores the result as subject-to-cluster mappings. A SCAR request only needs identity resolution plus a graph lookup.

That is why SCAR can answer “where can this user go?” in one shot instead of repeating SelfSubjectAccessReview across every workspace.

Debug endpoint

Graph snapshot
GET /debug/graph

Returns the current in-memory graph snapshot so you can inspect which subjects map to which clusters.
