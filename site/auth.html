Authentication flow

How identity flows from an MCP client through to kcp workspace access.

OAuth 2.1 with Dynamic Client Registration

MCP clients discover Keycloak metadata, register dynamically, and then run the authorization code flow. In the Kind stack, Keycloak is configured to allow dynamic client registration and to attach an audience mapper so issued access tokens include aud: kcp.

This is the key compatibility move: the AI client gets a normal OAuth token, but kcp still accepts it natively because the token audience matches the kcp OIDC configuration.

Token validation chain

  1. 1
    Bearer token.The first resolver calls kcp TokenReview and extracts the authenticated user and groups.
  2. 2
    Client certificate.Client certificates signed by the CA bundle in --client-ca-file authenticate directly, following standard Kubernetes delegated authentication.
  3. 3
    Front-proxy headers.X-Remote-User, X-Remote-Group, and X-Remote-Extra-* are trusted only when the caller presents a client certificate signed by --requestheader-client-ca-file.

Security: trusted headers

Header trust is gated on requestheader client-certificate mTLS: X-Remote-* headers are honored only from callers presenting a client certificate signed by --requestheader-client-ca-file (optionally restricted by --requestheader-allowed-names). This is the same pattern as the Kubernetes API server aggregation layer, so there is no unauthenticated header-trust mode anymore.
